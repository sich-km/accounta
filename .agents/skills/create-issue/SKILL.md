# Accounta: Create GitHub Issue

自然言語の開発依頼を**1件のGitHub Issue**へ変換する。ユーザーが `$create-issue <依頼>` を実行したら、内容を把握し、重複確認後にGitHubへ登録する。**ブランチ作成、コミット、コード変更、PR作成はしない。**

## 入力と例

- `$create-issue ダッシュボードのB/SをChart.jsで表示する`
- `$create-issue v0.5 予算実績の月別比較グラフを追加する`
- `$create-issue [v0.6] 固定資産一覧の検索条件を改善する`
- 入力が機能の提案・改善・不具合報告であれば、種別に応じたIssueを1件作る。複数の独立した機能が列挙された場合は、勝手に多数登録せず切り分けを相談する。
- 指示にバージョンが明示されている場合、現在ブランチのバージョンと矛盾しないか確認し、矛盾時は登録前に確認する。
- 先に `$create-branch v0.5` でバージョンを開始し、このスキルでやることを随時追加する。全Issueや実装順を事前に確定する必要はない。
- 引数が `v0.5` だけならIssue内容が不足しているため、やることを短く尋ねる。バージョン開始の意図が明らかなら `$create-branch v0.5` を案内し、このスキルでブランチを作成しない。
- Issue登録は実装開始やリリースの指示ではない。登録後は結果を報告して終了する。

## 1. 安全な事前確認

1. Codexの**現在の作業ディレクトリ**で `git rev-parse --show-toplevel`, `git branch --show-current`, `git remote get-url origin` を実行する。Git管理下でない、detached HEAD、origin不在の場合は停止する。
2. `origin` の参照先が `sich-km/accounta` であることを確認する。HTTP(S)・SSH等の表記差は許容するが、**異なるリポジトリなら停止**する。ユーザーのローカルPCの別作業ツリーを見たと推測しない。
3. `gh --version`, `gh auth status`, `gh repo view --json nameWithOwner --jq .nameWithOwner` でGitHub CLIと認証、対象リポジトリを確認する。`gh`未導入・未認証・権限不足・ネットワーク障害なら、Issueを作成したと主張せず状況と対処を説明する。
4. `AGENTS.md` と `docs/Accounta_開発プロセス.md` があれば読み、Issue作成についての追加ルールを尊重する。基本方針が競合する場合はユーザーに確認する。

## 2. 対象バージョンの判定

次の順序で**Issueの対象バージョン**を決定する。

1. ユーザーが `v0.5` 等を明示した場合はそれを優先し、ブランチから取得したバージョンと異なる場合は**確認してから**作成する。
2. 明示がなければ、`git branch --show-current` から `v数字.数字` または `v数字.数字.数字` の**独立した部分**を抽出する。原則として現在ブランチが `feature-v0.5` なら `v0.5` を抽出する。過去の形式のブランチを見つけた場合は、明示された入力との整合性を確認する。
3. `main`, `develop` のようにバージョンが特定できない場合、**コミットメッセージや最新Gitタグから推測しない**。「対象バージョンは何にしますか？」と短く確認し、登録を保留する。
4. 複数の異なるバージョンがブランチ名にある場合も確認する。

**重要：** GitHub IssueとGitブランチは、名前だけではGitHub上で自動的に関連付かない。バージョンはIssueタイトルと本文に記録し、バージョン別PRで `Refs #番号` として参照する。Issueごとの開発ブランチは作らない。

## 3. Issueタイトルと本文

- タイトルは **`[vX.Y] 対応内容`** または **`[vX.Y.Z] 対応内容`**。例：`[v0.5] ダッシュボードのB/SをChart.jsで表示する`。
- 日本語で、短い動詞付きの具体的な機能・不具合名にする。ユーザーの意図を維持し、ChartJS等の製品名は `Chart.js` に整えてよい。
- ブランチ名をタイトルに追加しない。`[feature-v0.5]` のような表記を避ける。
- 説明本文は次の構成とし、曖昧な内容を**確定要件のように創作しない**。

```markdown
## 目的
（利用者にとっての価値。1～2文）

## 対応内容
- [ ] （現在の実装を調査・確認）
- [ ] （実装する変更）
- [ ] （必要なテスト）

## 完了条件
- （観察可能・検証可能な条件）

## 開発情報
- 対象バージョン: v0.5
- Issue作成時のローカルブランチ: feature-v0.5
```

- `B/S` や仕訳等の会計情報では、組織間のデータ分離、集計元との一致、金額表示の整合性を必要に応じて完了条件に入れる。
- **現行コードで機能が存在するか未確認なら「現状確認」をタスクに残し、既存実装を確認済みと偽らない。**
- 入力が一文でも、自然な範囲で実装・テストのチェック項目を補う。UI詳細、技術方式やスコープが不明な点は「要確認」と記載する。
- ラベル・マイルストーン・担当者・プロジェクトは、ユーザーが指定したか、リポジトリに既存の明確な運用規約がある場合だけ設定する。**勝手に新規作成しない。** バージョン表記に加えてGitHub Milestoneの自動作成をしない。

## 4. 重複確認と登録

1. `gh issue list -R sich-km/accounta --state all --limit 100 --json number,title,url,state` 等で既存Issueを取得し、同一タイトル・同趣旨のIssueがないか調べる。候補があればURLを示し、**無断で重複登録しない**。検索が失敗した場合はその理由を示して停止する。
2. 登録対象のタイトル・説明を短く提示したうえで、ユーザーの明示的な `$create-issue` 依頼に基づき作成へ進む。必要情報が揃っていれば、追加の確認を要求しない。
3. GitHub CLIで `gh issue create -R sich-km/accounta --title "<title>" --body-file "<tempfile>"` を実行する。本文にはUTF-8の一時ファイルを用い、PowerShellでは必要に応じて `Set-Content -Encoding utf8` 等を使う。一時ファイルはリポジトリ外に作成して終了後に削除する。ユーザー入力をシェルコードとして評価しない。
4. GitHub CLIやCodexの外部書き込み承認が必要なら、その正規の承認操作に従う。認証や承認を迂回しない。
5. 作成結果のURLを取得し、`gh issue view <number-or-url> -R sich-km/accounta --json number,title,url,state` で内容を確認する。途中失敗時は**重複作成を避けるため既存Issueを再確認**してから再試行を検討する。
6. 登録したIssue番号・URL、タイトル、対象バージョン、作成時のブランチを短く報告する。未登録なら未登録と明記する。

## 禁止事項

- `main`, `develop`, 作業ブランチの自動切替・変更
- GitHub Issue以外への書き込み（コード変更、コミット、プッシュ、PR作成等）
- バージョンが不明なときの黙った推測や、他リポジトリへの登録
- Issueを作成していないのに作成済みと報告すること

## 次の開発フロー

Issue登録後は**現在のバージョン別ブランチ `feature-vX.Y` でそのまま開発する**。Issue単位のブランチは作らない。次バージョン開発時に `$create-branch feature-vX.Y`、まとまった開発が完了したら `$complete-branch feature-vX.Y` を使って `main` 向けPRを提出する。このSkill自身はGitブランチを変更しない。
