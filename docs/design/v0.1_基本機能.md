# Accounta v0.1 実装指示書

この文書は、[Accounta要求仕様書](../../SPEC.md)のv0.1を実装・検証するための制御上の基準を定義する。

特定のAI製品や実装担当者に依存しない。細かな実装方法は、既存コードの規約と自動テストを優先する。

現行実装を正とする。この文書と実装が異なる場合は実装を優先し、文書を更新する。v0.1で導入した機能の現行仕様を記述し、後続バージョンで追加した機能の詳細は [v0.2 固定資産管理台帳](v0.2_固定資産管理台帳.md) および [v0.3 仕訳帳と証憑管理](v0.3_仕訳帳と証憑管理.md) を参照する。

---

# 1. 実装範囲

v0.1で導入した機能:

- ユーザーIDによる認証とプロフィール
- CompanyとOrganizationによる所属管理
- システム管理者によるCompany管理
- 部門マスタ
- 予実管理科目マスタ
- 予算・実績明細
- ダッシュボード
- Excelエクスポート
- 初期データSeeder

v0.1の時点では仕訳、帳簿、財務諸表、データImportおよびBIダッシュボードを実装しない。仕訳、固定資産、仕訳用勘定科目、P/Lサマリーおよび会計学習の導線は後続バージョンで追加した。データImportは現行でも提供しない。

---

# 2. 技術基準

- Laravel 13
- PHP 8.3以上
- Blade
- Tailwind CSS
- Jetstream Livewire Stack
- MySQL 8.4 LTSを正式な完了判定DBとする
- UI Localeは日本語、Timezoneは `Asia/Tokyo` とする
- Excel出力は `maatwebsite/excel` を使用する

SPAおよび公開APIは追加しない。画面の絞り込みや明細行操作にはAlpine.jsを、ダッシュボードとプロフィールの一部にはLivewireを使用する。

実装はLaravelの標準機能と既存プロジェクトの構成を優先する。要求にない依存パッケージを追加しない。

---

# 3. 認証制御

- 認証識別子にはメールアドレスではなくユーザーID（`login_id`）を使用する
- ユーザーIDは前後空白を除去して英小文字へ正規化し、大文字小文字を区別せず一意にする
- 登録時にメールアドレスを要求せず、`users.email` はNullとする
- 登録時は組織名を必須とし、企業コード `km` の既存Companyへ新しいOrganizationを同一Transactionで作成する
- 登録時の所属部門コードと所属部門名は任意とし、両方入力した場合だけ初期Departmentを作成してUserへ紐付ける
- 登録ユーザーの種別は `user` とする
- プロフィール更新でユーザーID、Company、Organizationおよびユーザー種別を変更させない
- プロフィールから同一Organizationの所属部門（`users.department_id`）は変更できる
- 無効化した認証機能の画面とRouteを公開しない

無効化対象:

- メール認証
- パスワードリセット
- 二要素認証
- Passkeys
- API Token
- アカウント削除
- Jetstream Teams

Jetstreamの雛形Viewに条件分岐が残っていても、機能フラグが無効であるため画面は公開しない。

# 4. 所属・権限制御

Companyを最上位、Organizationを業務データの分離単位とする。

- UserはCompanyとOrganizationの両方に所属する
- Organizationは必ずCompanyに所属する
- Userは同一OrganizationのDepartmentを任意で所属部門として持つ
- Department、BudgetActualAccount、BudgetActualEntryはOrganizationに所属する
- UserのCompanyとOrganizationの組み合わせに矛盾を作らない
- 業務画面の取得・更新・削除はログインユーザーのOrganizationで制限する
- 他Organizationのリソースを指定した場合は、その存在を不用意に開示しない

ユーザー種別:

- `admin`: Company管理が可能なシステム管理者。所属Organizationの部門マスタと予実管理科目マスタも管理できる
- `company_admin`: 所属Organizationの部門マスタと予実管理科目マスタを管理できる会社管理者
- `user`: 部門マスタと予実管理科目マスタを参照できる一般ユーザー

マスタ管理可否は `User::canManageMasters()`（`admin` または `company_admin`）で判定する。

`users.user_type`はDB上では拡張しやすい文字列コードとして保持し、アプリケーションでは`App\Enums\UserType`のbacked enumで管理する。

Companyにはシステム用の特別種別を設けない。Company情報の登録・更新では企業コード、企業名および会計年度開始月を変更可能とする。削除はシステム管理者だけが、自身の所属Companyではなく、OrganizationもUserも持たないCompanyに限り実行できる。

部門マスタ、予実管理科目マスタおよび後続バージョンの仕訳用勘定科目マスタは、通常ナビゲーションの「管理」から開く管理トップ画面へ配置する。`admin` と `company_admin` だけに「管理」を表示する。会社情報管理カードは `admin` だけに表示する。

# 5. マスタ制御

DepartmentとBudgetActualAccountに共通する制御:

- コードはOrganization内で一意にする
- コードと名称は保存前に正規化する
- 削除機能は提供せず、有効・無効を切り替える
- `admin` と `company_admin` は一覧表示、登録、編集および有効・無効切替ができる
- `user` は一覧表示だけができ、登録、編集および有効・無効切替はできない
- `user` の画面には登録、編集および有効・無効切替の操作を表示しない
- 無効なマスタは新規の予算・実績明細で選択できない
- 既存明細が参照している無効なマスタは維持できる
- 他Organizationのマスタを参照・変更できない
- 一覧はコード昇順、同一コードはID昇順とし、1ページ50件でページネーションする

BudgetActualAccountは資産、負債、純資産、収益、費用の区分を保持する。Table名は `budget_actual_accounts`、明細Table名は `budget_actual_entries` とする。

---

# 6. 予算・実績制御

BudgetActualEntryは集計結果ではなく独立した明細として保存する。

- 予算と実績は区分（`budget` / `actual`）によって識別する
- 同一の年月、部門、予実管理科目および区分に複数明細を許可する
- 予算と実績を直接関連付けない
- 対象年月はDB上で月初日として保持する
- 金額は小数2桁までとし、0、正数、負数を許可する
- 登録元は画面入力させない。DBの `source` Columnは既定値 `manual` とし、アプリケーション層では読み書きしない
- DepartmentとBudgetActualAccountはBudgetActualEntryと同じOrganizationに限定する
- 一覧の既定は対象年月の降順、同一年月はID降順とする
- 一覧は対象区分、会計年度、月、部門、予実管理科目で絞り込める
- 表示件数は50、100、150、200件から選択でき、既定は50件とする
- 会計年度の既定値は会社の会計年度開始月に基づく当年度とする
- 絞り込み条件はユーザーごとにCacheへ保存し、`reset_filters` で初期化する
- 削除は選択した明細だけを対象とする

通常ナビゲーションのラベルは「予実管理」、画面見出しは「予算・実績」とする。

v0.1の実績は手入力する。仕訳から集計できる会計実績は別データとして扱い、予実明細へは自動反映しない。

# 7. ダッシュボード・プロフィール

ダッシュボードでは、ログインユーザーのOrganizationを基準に次を表示する。

1. P/Lサマリー（仕訳から会計年度単位で集計。Livewire）
2. B/Sサマリー（現行はプレースホルダ表示。Livewire）
3. 固定資産（保有中の件数、取得価額合計、帳簿価額合計）
4. 予実サマリー（会計年度単位の予算・実績比較。Livewire）
5. 管理（有効な部門数、有効な予実管理科目数、有効な仕訳用勘定科目数）

会計年度の選択値はユーザーごと・セクションごとにCacheへ保存する。ヘッダーから所属OrganizationのExcel Workbookをダウンロードできる。P/L、B/S、固定資産および仕訳用勘定科目の詳細は後続バージョンの設計書を正とする。

通常ナビゲーションの順は、ダッシュボード、仕訳、固定資産、予実管理、会計学習、権限者向けの管理とする。

プロフィールでは現在のCompany（企業コード、企業名、会計年度開始月）、Organization、ユーザー種別および所属部門を表示する。Company、Organizationおよびユーザー種別はプロフィールから変更させない。所属部門は同一Organization内で変更できる。

# 8. Excelエクスポート制御

- 認証済みユーザーだけが実行できる
- ログインユーザーのOrganizationだけを出力する
- 各データを別Sheetに分ける
- 見出し行は英語、Sheet名は日本語とする
- 各Sheetの列幅は、見出しと通常のデータがExcelで読みやすく表示される幅に調整する
- 無効なマスタも出力する
- 文字列を意図せずExcel数式として評価させない
- 同期Downloadとし、出力履歴をサーバーへ保存しない
- Import機能は作らない

Sheet順:

1. `まとめ`
2. `仕訳帳`
3. `固定資産管理台帳`
4. `予実管理`
5. `部門マスタ`
6. `予実管理科目マスタ`
7. `会社・組織情報`（`admin` のみ）

`company_admin` と `user` のWorkbookには `会社・組織情報` を出力しない。`まとめ`、`仕訳帳` および `固定資産管理台帳` の内容は後続バージョンの設計書を正とする。

予実管理Sheetの見出し:

| 順序 | Heading | 値 |
| --- | --- | --- |
| 1 | `Period` | 対象年月（Excel日付、表示は `yyyy-mm`） |
| 2 | `Year` | 年 |
| 3 | `Month` | 月 |
| 4 | `DepartmentCode` | 部門コード |
| 5 | `BudgetActualAccountCode` | 予実管理科目コード |
| 6 | `Type` | `budget` または `actual` |
| 7 | `Amount` | 金額 |
| 8 | `Memo` | メモ |

部門マスタSheetの見出しは `DepartmentCode`、`DepartmentName`、`IsActive`。予実管理科目マスタSheetの見出しは `BudgetActualAccountCode`、`BudgetActualAccountName`、`AccountType`、`IsActive`。会社・組織情報Sheetの見出しは `CompanyCode`、`CompanyName`、`FiscalYearStartMonth`、`OrganizationName`、`OrganizationType`。

# 9. 初期データ

`DatabaseSeeder` は次を順に実行する。

- `InitialTenantSeeder`
- `DepartmentSeeder`
- `BudgetActualAccountSeeder`
- `LedgerAccountSeeder`
- `JournalEntrySeeder`
- `BudgetActualEntrySeeder`
- `FixedAssetSeeder`

`InitialTenantSeeder` は次を再現可能に作成する。

- 企業コード `km`、企業名 `KM`、会計年度開始月1月のCompany
- 名称 `KM`、種別 `company` の初期Organization
- `admin` ユーザー
- `company_admin` ユーザー
- `user1` ユーザー

部門マスタと予実管理科目マスタは、存在するすべてのOrganizationへ再実行可能な方法で登録する。仕訳用勘定科目、仕訳、予算・実績明細および固定資産のサンプルデータ内容は後続バージョンの設計書および `docs/DatabaseSeeder_仮定法人.md` を正とする。

Seederは再実行可能とし、不要な重複を作らない。初期パスワードはランダムに生成し、ソースコードへ固定値を保存しない。初回作成時だけコンソールへパスワードを表示する。

---

# 10. データ整合性・セキュリティ

- 所属関係はApplicationのValidationだけでなくDB制約でも保護する
- 外部キーで参照中の主要データを不用意に削除できないようにする
- リクエストから所属Organizationやサーバー管理項目を自由に設定させない
- 認証、権限、入力Validation、Organization分離をサーバー側で実施する
- Excelへ出力する文字列を安全に扱う

---

# 11. 自動テスト

少なくとも次をFeature Testで確認する。

- ユーザーIDによる登録・ログインと重複拒否
- 無効化した認証機能を利用できないこと
- 登録失敗時に不完全なUserやOrganizationが残らないこと
- 登録時に既存の `km` Companyへ新しいOrganizationを作成すること
- DepartmentとBudgetActualAccountの登録、編集、有効・無効切替
- DepartmentとBudgetActualAccountに対するユーザー種別ごとの表示・変更権限
- マスタコードの重複拒否と正規化
- 予算と実績の登録、一覧、編集、削除
- 同一条件の複数明細
- 年月、金額およびマスタ選択の主要な入力エラー
- 予算・実績一覧の会計年度・月・区分などの絞り込みと表示件数
- 他Organizationのデータを参照・変更できないこと
- Company管理の権限、登録、更新および条件付き削除
- プロフィールでの所属部門更新とユーザーID変更不可
- Seederの再実行性
- Excelの日本語Sheet名、列幅、ユーザー種別ごとの出力内容、Organization分離および文字列の安全性

後続機能のTestは各バージョンの設計書を正とする。

# 12. v0.1 完了条件

次をすべて満たした場合にv0.1完了とする。

- 要求仕様書のv0.1機能を操作できる
- 対象外として無効化した認証機能が意図せず有効になっていない
- 全Feature Testが成功する
- MySQL 8.4で全MigrationとFeature Testが成功する
- フロントエンドの本番Buildが成功する
- 重大な既知不具合がない

完了判定は、機能が存在することだけでなく、権限、Organization分離、入力失敗および正式DBでの検証結果を含めて行う。後続バージョンで追加した機能の完了判定は、当該バージョンの設計書を正とする。

# 13. 実装時の運用

- 要求を満たす最小限の変更を行う
- 既存のコード規約とテスト構成に合わせる
- 変更した振る舞いには対応するテストを追加する
- この文書の範囲を超える機能は後続バージョンの設計書に従う
- 要求が曖昧でデータ構造や権限に影響する場合は、実装前に確認する
- 内部実装だけの変更では要求仕様書を更新しない
- 実装とこの文書がずれた場合は、実装を正としてこの文書を更新する
