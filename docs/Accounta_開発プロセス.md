# Accounta 開発プロセス

## 1. 基本方針

Accountaは個人開発・技術検証を前提とし、管理負担を最小限にする。構想は`docs/Accounta_サービス構想.md`および`docs/Accounta_機能構想.md`に、実装タスクはGitHub Issuesに管理する。実装済みの状態はコードとテストで確認し、機能一覧をMarkdownで二重管理しない。

## 2. Gitブランチ

`develop`は今後の開発フローで**使用しない**。GitHubの既存`develop`ブランチは、必要に応じて移行後に削除を判断し、Skillで勝手に削除しない。

| ブランチ | 用途 |
|---|---|
| `main` | 安定版・統合済みコード。直接コミット・pushしない。 |
| `v0.5`、`v0.6`など | **バージョン単位の開発・リリース用ブランチ**。複数Issue・改修を同じブランチで進め、まとまった時点でmain向けPRを作る。 |

最初にバージョンブランチを作り、その後でやることをIssueとして随時追加する。開始時点で全Issueやリリース範囲を決める必要はない。既存の命名に合わせて `vX.Y` を使い、別のリリース専用ブランチは作らない。

次のバージョンを開始する際は、原則として**前バージョンのPRがmainにマージ済み**であることを確認する。そうしないと新しいブランチへ前バージョンの変更が引き継がれない。

## 3. GitHub Issues

Issueは機能追加・改善・不具合などを必要時に登録する。**Issueごとの専用ブランチは作成しない**。

- タイトル: `[v0.5] ダッシュボードのB/SをChart.jsで表示する` のように、対象バージョンと対応内容を記載する。
- 本文: 目的、対応内容、完了条件。コードから判定できない要件や設計判断の理由はIssue/PRに残す。
- 現在のバージョンが未決定なら、Issue登録時に明示する。GitHub Milestonesは必要になったときだけ使う。
- Issueは個別に作成・更新できるが、コードをmainへ統合する単位はバージョン別PRとする。

## 4. Codex・Cursorの基本操作

Codexでは次の順序で操作する。

```text
$create-branch v0.5
$create-issue ダッシュボードのB/SをChart.jsで表示する
$create-issue 固定資産一覧を改善する
（v0.5で実装・検証・コミットし、必要なIssueを随時追加する）
（リリースできる変更がまとまったら）
$complete-branch v0.5
```

- `$create-branch v0.5` は作業状態を確認し、**GitHubの最新mainからGitHub側に `v0.5` を作成**する。その後fetchし、ローカルの `v0.5` へ切り替えて `origin/v0.5` を追跡する。
- `$create-issue <やること>` は現在の `vX.Y` からバージョンを判定し、`[vX.Y] 対応内容` のIssueを追加する。Issue登録だけでは実装は開始しない。バージョンだけの指定はIssueの内容にならない。
- `$complete-branch v0.5` は差分・検証結果を確認し、対象変更をコミット・pushして `v0.5` → `main` のPRを作成する。実行は利用者がリリースの区切りを指示したときとし、Issue数による自動実行はしない。
- PRには含めた変更と関連Issueをまとめ、未対応Issueがあれば明記する。全Issueの完了をPR作成の条件にはせず、未対応Issueを完了扱いにしない。
- `$complete-branch` はPR確認後に終了する。PRのマージ、IssueのClose、ブランチ切替は行わない。
- PRを確認・マージした後、関連IssueをClosedにし、次バージョンを開始する。ブランチ削除は必要に応じて手動で行う。

Cursorでは同じ順序で `/create-branch v0.5`、`/create-issue <やること>`、`/complete-branch v0.5` を使う。詳細手順は `.agents/skills/` を共通の参照先とし、`.cursor/skills/` から読み込む。

## 5. リリース・品質

mainへの統合前に、適切なテストとPR差分確認を行う。会計処理の貸借一致・金額精度・集計整合性、会社・組織データの分離、認可の確認を重視する。正式なリリースを識別する場合はmainの対象コミットにGitタグ（例:`v0.5.0`）を付ける。タグ作成はSkillで自動実行しない。

Git操作前には未コミット変更・秘密情報・対象リポジトリを確認し、force push、無断のreset、作業変更の破棄、PRの無断マージをしない。
